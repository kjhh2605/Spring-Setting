# PR 구성과 작성

## 기능 작업과 stacked PR

기능 작업은 사람이 검토할 작업 단위로 나누어 **stacked PR**로 작성합니다. 기능 하나가 여러 PR에서 완성되어도 됩니다. 각 PR은 [PR 크기 기준](reviews.md#pr-크기)을 지키고 더 작은 커밋들을 포함합니다. 분리할 책임이 없는 작은 기능은 하나의 PR로 완결하며, 개수를 맞추기 위한 빈 준비 PR은 만들지 않습니다.

1. **구현 전 계획:** PR마다 리뷰어가 판단할 내용·대상 범위·선행 PR·완료 조건·검사를 정하고, 그 안의 작은 커밋 순서를 정합니다. 계획은 대화나 임시 메모에 유지하며 기능 전체를 구현한 뒤에만 분할하지 않습니다.
2. **브랜치와 diff:** 첫 PR은 실제 기본 브랜치를, 의존하는 다음 PR은 직접 선행 PR의 브랜치를 base로 둡니다. 독립적인 변경은 기본 브랜치에서 나눕니다. 후속 PR을 모두 기본 브랜치와 비교해 선행 변경까지 중복 제출하지 않습니다.
3. **PR별 완결:** 기존 코드·검토된 선행 PR·현재 diff만으로 변경을 판단할 수 있어야 합니다. 기동과 기존 동작을 유지하고 필요한 테스트·설정·현재 계약 문서를 함께 포함합니다. 전체 기능이 미완성이어도 되지만 후속 구현이 필요한 경로를 사용자에게 노출하거나 실패하는 검사를 남기지 않습니다.
4. **검토와 반영 순서:** 각 단위가 준비되면 PR을 작성하고 선행 PR·검토 순서·이번 범위를 표시합니다. 선행 PR이 반영되기 전에도 검토할 수 있지만 반영은 의존 순서대로 진행합니다. 해당 단위의 구현·필수 검증이 미완료면 Draft로 표시합니다.
5. **선행 변경 반영:** 선행 PR이 수정·병합되면 후속 PR의 base/head SHA와 diff를 다시 확인합니다. 기준 변경으로 달라진 범위·기존 댓글의 위치를 알리고 영향을 받는 검사와 최종 연결을 확인합니다. 정상 검증 뒤 변화가 없으면 같은 검사를 반복하지 않습니다.
6. **이력 보존:** 사람이 커밋별 흐름을 추적하도록 의미 있는 커밋을 보존하는 merge commit을 기본으로 합니다. squash 등 다른 방식은 명시된 사용자 선택을 따릅니다. 선행 PR을 squash한 경우 후속 브랜치에서 변경이 중복되지 않는지 확인합니다. 이력 재작성·푸시·병합은 [승인 절차](approvals.md#승인-절차)를 따릅니다.

예를 들어 `main ← 계정 연결 PR ← 로그인 조립 PR`에서 두 번째 PR은 계정 연결 이후의 변경만 보여 줍니다. 신규 API 선언만 분리해 사용 맥락이 사라지거나, 테스트 전체를 뒤 PR로 미루는 분할은 피합니다. 기능 활성화를 나누어야 하면 안전한 기본 동작과 활성화·복구 조건을 명시합니다.

작은 리뷰 단위의 조건과 의존 변경 구성은 [Google Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html), GitHub의 [stacked PR 안내](https://docs.github.com/en/pull-requests/get-started/about-pull-requests)와 [병합 방식](https://docs.github.com/en/pull-requests/reference/pull-request-merges)을 참고합니다. 이 절의 작업 방식은 기존 게시·승인 범위를 확대하지 않습니다.

## PR 작성

공통 [유형](change-types.md)·[라벨](github-publishing.md#라벨-운영)·[AI 작성 절차](github-publishing.md#ai-작성-절차)와 [PR 크기 기준](reviews.md#pr-크기)을 해당 원본에서 확인합니다.

제목은 `type(scope): 최종 변경 결과` 형식으로 작성하며 `scope`는 생략할 수 있습니다. 유형은 [작업 유형](change-types.md)의 11개 중 하나, 범위는 실제 모듈·영역 이름을 사용합니다. 예: `docs(onboarding): 초기 실행 절차를 정리한다`. 호환성을 깨는 변경은 `feat(api)!: ...`처럼 `!`를 붙이고 `compatibility:breaking` 라벨과 전환 설명을 함께 작성합니다.

PR의 대표 라벨은 제목 유형과 일치시킵니다. 예를 들어 `fix(user): ...`에는 `type:fix`를 지정합니다. 유형은 최종 diff의 목적을 기준으로 정하므로 조사 이슈에서 시작한 기능 구현 PR은 `feat`가 될 수 있습니다. 이슈의 유형을 기계적으로 복사하지 않습니다.

본문은 [PR 양식](../../.github/pull_request_template.md)의 순서대로 작성하고 안내 주석은 제거합니다. 간단한 변경은 필수 항목마다 한 문장으로 충분합니다. 관련 이슈가 없으면 `없음`으로 적으며 형식만 맞추기 위해 이슈를 만들지 않습니다.

| 유형 | 주요 변경과 검증에 포함할 정보 |
| --- | --- |
| `feat` | 핵심 흐름, 완료 조건의 충족 여부, 정상·실패 경로 검증 |
| `fix` | 발생 조건·원인·수정 후 결과, 재현 테스트의 실패→성공 근거 |
| `docs` | 문서의 원본 근거, 구현과의 일치, 링크·경로·예제 확인 |
| `refactor` | 책임·의존성의 변경 이유와 기존 동작·계약 보존 근거 |
| `perf` | 같은 데이터·환경·명령으로 측정한 전후 수치, 측정 한계와 회귀 검사. 미측정이면 개선을 입증했다고 쓰지 않음 |
| `test` | 새로 검증하는 행동·실패 조건과 실제 테스트 결과 |
| `build` | 의존성·빌드·패키징 영향과 변경 후 실행 결과 |
| `ci` | 실행 조건·권한·검사 절차 변화와 검증 결과. 실제 CI 미실행은 로컬 검사와 구분 |
| `chore` | 구체적인 관리 대상·목적과 그 대상에 맞는 확인 결과 |
| `revert` | 대상 PR·커밋, 되돌리는 이유, 복구 상태와 데이터·설정 복구 제약, 복구 검증 |
| `investigation` | 사용한 자료·실험, 근거 있는 결론과 미해결 질문 또는 후속 작업 |

`주요 변경`에는 확인한 base/head SHA, 변경 파일 수·추가/삭제 줄 수와 커밋 검토 순서를 짧게 적습니다. stacked PR은 선행 PR과 이번 차이를 표시하고 실제 후속 PR이 있으면 연결합니다. 단순한 PR은 한 문장으로 요약할 수 있습니다. 통계는 분할 판단의 근거이며 품질 점수가 아닙니다.

검증에는 검사 대상 SHA·실제 명령·핵심 정상/거부/경계 조건과 결과를 기록합니다. mock 대체와 실제 통합 검사를 구분하고, 집중 검사나 최종 CI 통과를 모든 중간 커밋의 통과로 표현하지 않습니다. 필수 명령과 문서 변경의 기준은 [검증과 완료](../../AGENTS.md)를 따릅니다. `영향과 리뷰 포인트`에는 현재 단위를 반영할 수 있는 이유·의존 순서를, 호환성 파괴·데이터 변경에는 적용 순서와 복구 제약을 적습니다. 해당 영향이 없으면 이 선택 항목은 생략합니다.

이슈 완료 조건을 모두 해결하는 PR에만 `Closes #123`을 사용합니다. 부분 작업·참고는 `Refs #123`으로 연결합니다. 번호는 형식 예시이므로 실제 존재와 관계를 확인해 교체합니다. 자동 종료는 기본 브랜치를 대상으로 한 PR이 병합될 때 적용되므로 다른 대상 브랜치에서는 종료를 보장하지 않습니다. [이슈와 PR 연결](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

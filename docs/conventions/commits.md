# 커밋과 브랜치

## 커밋

유형 선택은 [작업 유형](github-publishing.md#작업-유형과-이슈-양식), 작업 권한과 완료 검증은 [루트 지침](../../AGENTS.md)이 원본입니다.

### 메시지와 변경 단위

- 제목은 `type(scope): 한국어 변경 요약`으로 작성하고 `거부`, `추가`, `생성`, `검증`처럼 명사형으로 끝냅니다. `~한다`형은 사용하지 않습니다. 유형은 실제 diff의 목적에 맞게 선택하고 `scope`는 실제 모듈·영역이며 생략할 수 있습니다. 예: `fix(user): 빈 표시 이름 등록 차단`.
- 호환성 파괴는 `type(scope)!: ...`로 표시하고 본문에 깨지는 계약과 전환 방법을 적습니다. 비단순 변경은 문제·변경 이유와 실제 검증 근거를 짧게 설명합니다. 제목만으로 이유까지 명백한 변경은 본문을 생략할 수 있습니다. 실제 관련 이슈만 연결하며 대화·실행 로그 전체를 복사하지 않습니다.
- 커밋은 사람이 한 변경 이유를 이해하고 검증할 수 있는 작은 단계입니다. PR보다 작은 단위를 기본으로 하며 고정 줄 수·파일 수·커밋 개수를 목표로 삼지 않습니다. 설명에 별개 정책이나 책임을 나열해야 하면 분리합니다.
- 해당 행동의 구현·필수 테스트·계약 문서를 함께 묶습니다. 파일·계층·구현/테스트 종류별로 기계적으로 나누지 않습니다. 동작을 보존하는 준비 리팩터링이나 독립적인 문서·테스트 보강도 이유가 명확하면 한 커밋이 될 수 있습니다.
- 코드 변경의 중간 커밋은 관련 집중 검사 통과 후 자동 생성합니다. 코드·빌드·실행 설정 작업의 완료 시점에는 [루트 전체 검증](../../AGENTS.md#검증과-완료)을 수행합니다. 문서만의 변경에는 링크·경로·일관성과 `git diff --check`를 적용합니다.
- 실패하거나 필수 집중 검사를 수행하지 못한 단위는 자동 커밋하지 않습니다. 이미 만든 중간 커밋 뒤 전체 검사에서 문제가 발견되면 수정·검증 후 새 커밋으로 보완하고, 중간 커밋을 전체 검증 완료로 보고하지 않습니다.
- 조사·리뷰만 요청받은 경우 커밋할 변경을 임의로 만들지 않습니다. 커밋하지 말라는 요청이 있으면 자동 커밋을 하지 않습니다.

비단순 커밋의 메시지 예시입니다. 검증 내용은 실제 결과로 작성합니다.

```text
fix(auth): 다른 발급자의 Access Token 거부

같은 키로 서명된 다른 발급자의 토큰도 수용되는 문제를 막기 위해
설정한 issuer와 일치하는지 검증한다.

검증: 정상 issuer 수용과 다른 issuer 거부 회귀 검사
```

### 작업 중 커밋 체크포인트

**한 변경 이유가 검증되면 커밋합니다.** 앞선 커밋부터 읽으면 결정과 구현 순서가 드러나야 합니다. 작은 커밋을 만들기 위해 결합된 코드를 삭제·재작성하거나 기존 Bean 등록을 임시로 제거하지 않습니다. 논리적 분리와 설명의 근거는 [Git 기여 가이드](https://git-scm.com/docs/SubmittingPatches), 각 중간 상태의 빌드·실행 조건은 [Linux 기여 가이드](https://docs.kernel.org/process/submitting-patches.html#separate-your-changes)를 참고합니다.

- **구현 전 분리:** 여러 책임에 걸친 요청은 예정 커밋마다 목적·대상 파일 또는 hunk 범위·선행 의존성·집중 검사 명령을 대화에서 짧게 제시합니다. 문서 전용 단위는 링크·경로·일관성과 `git diff --check`를 검사로 적습니다. 계획은 대화나 임시 파일에서 관리하며 상시 문서에 작업 일지로 남기지 않습니다.
- **한 단위씩 진행:** 현재 단위를 구현하고 관련 집중 검사와 diff 검토를 마치면 즉시 커밋합니다. 이 체크포인트를 통과한 뒤 같은 작업 트리에서 다음 단위를 시작합니다. 커밋마다 해시·목적·실제 검사 결과를 짧게 보고합니다.
- **단위별 계약 검토:** 이번 변경에 적용할 지침과 계약의 선언·구현·호출부·테스트를 함께 대조합니다. Web 변경은 Request에서 Command/Query로의 변환과 Controller·Docs 인터페이스의 시그니처·검증 선언, 모듈 간 변경은 공개 계약과 소비자를 해당 단위에서 확인합니다. 무관한 계약까지 검토 범위를 넓히지 않습니다.
- **단위의 완결성:** 선행 커밋까지 적용한 현재 상태가 컴파일되고 관련 집중 테스트를 통과해야 합니다. 선행 변경에 의존할 수 있지만 후속 코드가 없어 기동하지 않거나 검사가 실패하는 상태는 남기지 않습니다. 테스트의 의도한 실패는 작업 중 확인하고 구현과 함께 통과 상태로 커밋합니다.
- **분리 판단:** 현재 변경을 설명·검증하는 데 별개의 판단이 필요한지 확인합니다. 결합 때문에 함께 완결해야 한다면 그 이유를 짧게 적고 계획을 갱신합니다. PR의 줄 수 기준에 도달할 때까지 변경을 누적하지 않습니다.
- **검증 상태 일치:** 검증한 파일과 커밋할 파일·hunk가 같은 동작을 구성해야 합니다. 부분 스테이징 시 아직 커밋하지 않을 구현으로 검사가 통과한 것은 아닌지 확인합니다. 불일치하면 커밋할 상태를 분리해 필요한 검사를 실행합니다.
- **목적 기준 유지:** 사용자가 하나의 기능을 요청했다는 사실이나 유스케이스가 연결된다는 이유만으로 전체 변경을 한 커밋으로 묶지 않습니다. 독립적으로 검토할 책임과 의존 관계를 기준으로 나눕니다. 여러 단위의 구현을 끝낸 뒤 한꺼번에 커밋하거나 마지막에만 이력을 나누는 방식을 기본으로 사용하지 않습니다.
- **검사 실패·미실행:** 필수 집중 검사가 실패하거나 승인·환경 문제로 실행되지 못하면 해당 단위의 커밋과 변경 확대를 보류합니다. 삭제 없는 진단·수정은 계속하고, 다른 독립 단위의 작업이 필요하면 별도 작업 트리에서 분리합니다. 승인·미검증 보고는 기존 규칙을 따릅니다.
- **마지막 확인:** 코드·빌드·실행 설정 작업은 모든 단위의 집중 검사·계약 검토와 알려진 수정 사항을 마친 뒤 [전체 검증](../../AGENTS.md#검증과-완료)을 수행합니다. 전체 검증에서 새로 발견한 문제는 수정·관련 검사 후 별도 후속 커밋으로 남기며 최종 변경에 필요한 전체 검증을 마칩니다. 검사 횟수를 제한하거나 필요한 재검증을 생략하지 않습니다. 문서 전용 변경의 검증 예외와 사용자 커밋 금지 지시는 그대로 적용합니다.

커밋 분리와 PR 분리는 각각 점검합니다. 여러 커밋으로 만들었어도 독립 목적을 한 PR에 누적하지 않으며, [PR 크기와 AI 리뷰](reviews.md#pr-크기)의 사전 분리 기준을 적용합니다.

### 브랜치와 스테이징

- 기본 브랜치는 원격 HEAD 등 저장소의 실제 정보로 확인합니다. 기본 브랜치에서 수정 작업을 시작하면 사용 중이지 않은 작업용 브랜치를 자동 생성하고 그 브랜치에 커밋합니다. 기본 브랜치를 식별할 수 없으면 이름을 추정하지 않습니다.
- 작업 브랜치 이름은 `<type>/<짧은-작업명>`을 기본으로 하되 기존 팀·사용자가 지정한 이름이 있으면 따릅니다. 이미 해당 작업 브랜치에 있으면 계속 사용합니다.
- 시작 시 작업 트리와 staged diff를 확인합니다. 이번 작업의 파일·hunk만 명시적으로 stage하고 커밋 직전 staged diff·포함 경로를 확인합니다. 다른 작업자의 변경이나 비밀값·생성물을 함께 커밋하지 않습니다. 변경 소유권이 섞여 안전하게 분리할 수 없으면 커밋을 보류하고 필요한 구분을 알립니다.
- 자동으로 허용하는 이력 작업은 새 커밋 생성입니다. `commit --amend`, rebase, reset과 브랜치 삭제는 [승인 절차](approvals.md#승인-절차)를 따릅니다. 옵션 순서나 명령 별칭이 달라도 같은 행위로 판단합니다.
- 커밋 후 식별자·변경 목적·실제 검사 결과와 남은 전체 검증을 보고합니다. 커밋 생성은 푸시·PR 생성·병합 권한이 아닙니다.

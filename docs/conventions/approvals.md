# 실행 전 승인 안내

## 승인 절차

[루트 작업 원칙](../../AGENTS.md#작업-원칙)의 확인 대상은 사용자의 실행 요청과 별도로, 실행할 내용을 요약한 뒤 승인을 받습니다. 승인은 요약한 대상·변경·실행 범위에 한정되며, 범위가 바뀌면 다시 확인합니다.

| 행위 | 실행 전 요약할 내용 |
| --- | --- |
| 푸시 | 원격·브랜치·포함 커밋, 원격 이력 변경·강제 옵션 여부 |
| amend·rebase·reset·브랜치 삭제 | 대상 커밋/브랜치, 공유 여부, 이력·작업 트리에 미칠 영향 |
| DB 데이터·볼륨 삭제 | 환경·DB/볼륨 식별자·삭제 범위, 복구 가능 여부 |
| DB·컨테이너 테스트 | 검사 명령·대상 테스트, 테스트 DB 생성과 데이터·컨테이너·볼륨 정리 범위 |
| 스키마 삭제를 포함한 앱 실행 | 실행 명령·활성 프로필·대상 DB, 시작·종료 시 스키마 생성·삭제 범위. 현재 `local`의 `create-drop` 포함 |
| 미커밋·보관한 작업을 잃는 Git 정리·복원 | 대상 경로·stash·worktree, 버려지는 변경, 복구 가능 여부 |
| PR 병합·닫기·삭제 | 저장소·PR 번호·최종 변경, 병합 대상과 방식·연동 CI, 동반하는 브랜치 삭제 여부 |
| 릴리스 게시 | 저장소·태그·대상 커밋·게시 내용과 자산, 연동 배포·CI 영향 |
| 배포 | 대상 환경·배포 버전/변경, 서비스·데이터 영향과 복구 방법 |

테스트 내부의 삭제는 개별 SQL마다 멈출 수 있다고 가정하지 않습니다. 삭제를 포함한 검사 전체의 생명주기를 실행 전에 요약하여 승인받습니다. 반복 실행이 필요하면 횟수·조건을 요약에 포함하고 그 범위를 넘는 실행은 다시 확인합니다. 승인이 없으면 DB 삭제가 없는 독립 검사부터 수행하고 나머지를 미검증으로 보고합니다.

앱 내부의 스키마 자동 삭제에도 같은 절차를 적용합니다. [빠른 시작](../../README.md#빠른-시작)의 `./gradlew bootRun`은 `local` 프로필을 적용하며, [실제 설정](../../src/main/resources/application-local.yml)의 `create-drop`에 따른 시작·종료 영향을 실행 전에 승인받습니다. 다른 프로필·IDE·JAR 실행도 명령 이름이 아니라 실제 설정과 대상 DB로 판단합니다.

`git clean`, `git restore`, `git checkout -- …`, `git stash drop/clear`, `git worktree remove`는 실제로 미커밋·보관한 작업을 잃는지 확인합니다. 요청에 필요한 소스 삭제·생성물 정리, 삭제 없는 조회·미리보기는 자동 범위를 유지합니다. `git restore --staged`처럼 작업 파일을 보존하는 스테이징 조정은 다른 작업자의 staged 변경을 보존하며 이번 작업 범위에서 수행합니다. `reset`은 결과가 비슷하더라도 기존 명시 승인 대상입니다.

사용자가 요청한 PR·이슈 생성·수정·댓글은 추가 확인 없이 수행합니다. 이 예외는 PR 닫기·병합·삭제를 일반 수정으로 처리하거나, 선행 푸시·DB 테스트의 확인을 생략하는 근거가 아닙니다. 초안 작성·리뷰 요청을 게시 권한으로 확대하지 않습니다. 릴리스 게시에는 기존 초안을 공개하는 경우도 포함합니다. PR 삭제는 행위 기준이며, 지원 여부를 확인하지 않고 존재하지 않는 CLI 명령을 가정하지 않습니다.

도구가 승인 UI를 제공하면 해당 요청에 위 요약을 담을 수 있습니다. 대화에서 받은 승인과 실행 도구의 권한 검사는 별개이며, 도구가 거부하면 승인 모드·규칙을 임의로 바꾸거나 다른 실행 경로로 우회하지 않습니다. `.rules`의 일치 여부가 행위의 승인 필요성을 결정하지는 않습니다. 정책 선택 이유는 [ADR-002의 승인과 외부 작업](../adr/002-agentic-coding-rules.md#승인과-외부-작업)을 참고합니다.
